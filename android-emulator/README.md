# Android device emulator

Эмуляция Android-устройства на всех уровнях, которые видит сайт: JavaScript
(`navigator`, `screen`, canvas, WebGL, Web Audio, шрифты), HTTP-заголовки и их
порядок, HTTP/2 SETTINGS, TLS ClientHello (JA3/JA4), исходящий IP и cookies.

Главный принцип: **одна личность, один источник истины.** Все слои читают один
и тот же выведенный профиль. Как только два слоя начинают вычислять одно и то же
значение независимо, они рано или поздно разойдутся — а расхождение между слоями
заметнее, чем любое отдельное «неправильное» значение.

```
профиль устройства ─┬─► JS-инъекция      (navigator, canvas, WebGL, audio, шрифты)
   (device + locale ├─► CDP-эмуляция     (UA, client hints, экран, DPR, часовой пояс)
    + seed)         ├─► fontconfig       (реальный набор шрифтов для DOM-раскладки)
                    └─► tlsproxy (Go)    (ClientHello, HTTP/2, порядок заголовков, IP)
```

## Почему прокси, а не только JavaScript

Браузеру можно назначить любой User-Agent, но нельзя изменить его TLS
ClientHello, набор HTTP/2 SETTINGS и порядок, в котором он пишет заголовки —
это зашито в Chromium. Поэтому браузер ходит через локальный MITM-прокси
(`tools/tlsproxy`, Go + uTLS), который переотправляет каждый запрос с
рукопожатием эмулируемого устройства.

Проверить, что получается на самом деле:

```
$ andro tls galaxy-s23-ultra
device:    galaxy-s23-ultra
template:  HelloChrome_131 (Chrome 131)
ja3:       3c2425354831091ec83bf312af5ae848
ja4:       t13d1516h2_8daaf6152771_02713d6af862
```

JA3/JA4 не берутся из таблицы — они вычисляются из ClientHello, который реально
будет отправлен. Захардкоженный «ожидаемый отпечаток» верен ровно до следующего
обновления uTLS, а потом уверенно врёт.

Обратите внимание: **JA3 у Chrome нестабилен по построению.** Начиная с M110
Chrome перемешивает порядок расширений в каждом соединении, поэтому одинаковый
JA3 от соединения к соединению — сам по себе аномалия. JA4 сортирует списки
перед хешированием и является тем значением, на которое стоит опираться.

## Установка

Из исходников (Linux):

```bash
npm install
npx playwright install chromium
node tools/fetch-fonts.mjs ./android-fonts   # набор шрифтов AOSP (OFL/Apache-2.0)
npm run build:proxy                          # нужен Go 1.25+
```

Из готового архива — Go не нужен, бинарники прокси уже внутри:

```bash
# macOS
tar -xzf android-emulator-macos.tar.gz
cd android-emulator-macos && ./install-macos.sh
```

```powershell
# Windows: распаковать zip, затем из каталога проекта
powershell -ExecutionPolicy Bypass -File .\install-windows.ps1
```

Собрать такой архив: `npm run release:macos`, `release:windows` или
`release:linux` (кросс-компилирует прокси под обе архитектуры платформы и
пакует всё в `dist/`).

Слой шрифтов работает **только на Linux** — Chromium читает fontconfig лишь
там. Подробности и обходной путь: [docs/macos.md](docs/macos.md),
[docs/windows.md](docs/windows.md).

## Панель управления

На Windows — двойной клик по `AndroidEmulator.exe`: он поднимает сервер и
открывает отдельное окно приложения без адресной строки и вкладок. Это не
второй Chromium — лаунчер находит уже установленный браузер и открывает его в
режиме `--app`, поэтому весит 6 МБ.

Везде — то же самое из терминала:

```bash
node bin/cli.js gui
```

Откроет локальный сервер на `http://127.0.0.1:7333`. В браузере — настройки
слева, живой экран устройства в телефонной рамке по центру, выведенная личность
и проверка справа. По экрану можно кликать и скроллить: это уходит обратно в
браузер настоящими touch-событиями, а картинка приходит CDP-скринкастом. Само
зеркалирование для сайта невидимо — эмулируемый браузер остаётся обычным
браузером.

Кнопка «Проверить эмуляцию» гоняет ровно те же проверки, что и `andro verify`,
в отдельной вкладке на локальном origin — видимая страница остаётся на месте.

В панели настраиваются: модель (с фильтром), 47 локалей, 158 часовых поясов
отдельно от локали, ориентация экрана, seed (в том числе случайный),
вышестоящий прокси, внешний IP, геопозиция, уровень заряда. Есть именованные
пресеты, скриншот устройства, очистка cookies и хранилища, полное стирание
состояния seed'а.

Смена локали подтягивает за собой пояс и координаты: это одна личность, и
оставить московскую точку под бразильской локалью — ровно то противоречие,
против которого весь проект и построен.

## Использование

Все команды запускаются **из каталога проекта**. Короткого имени `andro` в
системе по умолчанию нет — оно появляется только после `npm link`. Поэтому
базовый способ такой:

```bash
cd android-emulator-macos          # или -windows / -linux, куда распаковали

node bin/cli.js devices                                    # список устройств
node bin/cli.js tls   pixel-8-pro                          # JA3/JA4 профиля
node bin/cli.js verify pixel-8-pro --fonts ./android-fonts # проверить эмуляцию
node bin/cli.js open  galaxy-s23-ultra https://example.com --upstream socks5://user:pass@host:1080
```

Если хочется короткого `andro` из любого каталога — один раз выполните в
каталоге проекта `npm link`. Дальше в этом README команды показаны как
`andro ...`; читайте их как `node bin/cli.js ...`, если ссылку не делали.

Программно:

```js
import { launchDevice } from './src/index.js';

const session = await launchDevice({
  deviceId: 'galaxy-s23-ultra',
  locale: 'ru-RU',
  seed: 'account-42',                     // тот же seed → то же устройство
  upstream: 'socks5://user:pass@host:1080',
  publicIp: '203.0.113.7',                // для привязки WebRTC-кандидатов
  fontsDir: './android-fonts',
});

const page = await session.newPage();
await page.goto('https://example.com');
await session.close();
```

`seed` определяет всё «случайное»: дизеринг canvas и audio, уровень заряда,
параметры сети. Один и тот же seed воспроизводит устройство побайтово; разные
seed'ы дают разные устройства одной модели. Ничто в проекте не вызывает
`Math.random()` — иначе профиль «плыл» бы между запусками, и сайт, снявший
отпечаток дважды, увидел бы два разных устройства.

Состояние (cookies, localStorage, IndexedDB, локальный CA) живёт в
`profiles-data/<device>-<seedId>/` и переживает перезапуск: вернувшееся
устройство выглядит как вернувшееся, а не как только что созданное.

## Что эмулируется

**JS.** `navigator` (UA, платформа, ядра, память, языки, touch-points, plugins,
connection, battery, storage), `screen` и DPR, ориентация, media queries,
`userAgentData` с high-entropy hints, canvas (детерминированный дизеринг +
метрики текста), WebGL 1/2 (строки GPU, лимиты, список расширений, точность
шейдеров, `readPixels`), Web Audio (DSP-подпись SoC, 48 кГц), шрифты,
`enumerateDevices`, кодеки, разрешения, TTS-голоса, `window.chrome`.

**Поверхность API.** На Android нет `navigator.serial`, `navigator.hid`,
`navigator.keyboard`, `SharedWorker`, `showOpenFilePicker`, `queryLocalFonts`.
Оставить десктопные API, объявляя себя телефоном, — сигнал сильнее неверного
UA: пользователь не может «случайно» получить такую комбинацию.

**Сеть.** UA и client hints (низкоэнтропийные всегда, высокоэнтропийные — только
там, где браузер их и так отправляет: рассылать `sec-ch-ua-model` без
`Accept-CH` — отдельная аномалия), порядок заголовков отдельно для навигации,
XHR и подресурсов, HTTP/2 SETTINGS + `WINDOW_UPDATE` + порядок псевдо-заголовков
(`m,a,s,p` у Chrome против `a,m,p,s` у Go), TLS ClientHello, вышестоящий
SOCKS5/HTTP-прокси для IP.

**Согласованность личности.** Локаль, часовой пояс, `Accept-Language` и ожидаемая
страна выхода — одно целое. Если `Intl` говорит `Europe/Warsaw`, то IP должен
геолоцироваться в Польшу, а `Accept-Language` — начинаться с `pl`.

### Две детали, которые обычно делают неправильно

**UA-строка Android заморожена.** С Chrome 110 реальная версия ОС и модель
заменены на `Android 10; K` для всех устройств. Написать в UA настоящую модель —
интуитивный шаг и сразу улика: ни один реальный Chrome так не делает. Настоящие
значения едут в high-entropy client hints.

**Планшеты не содержат токена `Mobile`** в UA и отправляют
`sec-ch-ua-mobile: ?0`.

## Проверка

```
$ andro verify pixel-8-pro --fonts ./android-fonts
  ok    navigator.userAgent
  ok    UA string is the reduced Android form
  ok    WebGL UNMASKED_RENDERER
  ok    canvas toDataURL is stable within the session
  ok    AudioContext runs at 48 kHz (Android HAL)
  ok    Function.prototype.toString reports native source
  ...
  70/71 passed, 1 warning
```

Проверки бывают двух видов: сравнение наблюдаемого значения с профилем, который
его породил, и утверждения о внутренней согласованности, которые реальное
устройство нарушить не может (виден ли вьюпорт внутри экрана, совпадает ли
CSS-размер × DPR с физической матрицей, согласны ли `Notification.permission` и
`permissions.query`).

Отдельная группа проверок — целостность самих патчей: `userAgent` должен
оставаться аксессором на прототипе, а не собственным свойством экземпляра;
подменённый геттер должен называться `get userAgent` и сообщать `[native code]`;
`Function.prototype.toString.toString()` тоже должен сообщать `[native code]`.

Стабильность canvas и audio проверяется дважды **намеренно**: нестабильный хеш
между двумя снятиями в одной сессии — сигнал громче любого конкретного значения,
и это ровно тот режим отказа, который получается при наивной реализации шума.

`npm test` проверяет чистые функции без браузера: инвариант экрана, детерминизм
вывода профиля, отсутствие захвата модульной области видимости в
инъектируемых функциях, корректность нативных хелперов.

## Известные ограничения

См. [docs/limitations.md](docs/limitations.md); по платформам отдельно
[docs/macos.md](docs/macos.md) и [docs/windows.md](docs/windows.md). Кратко: патч нативного метода оставляет свой
кадр в stack trace; без `fontsDir` (и вообще на macOS/Windows, где Chromium не
читает fontconfig) набор шрифтов хоста виден DOM-раскладке; WebSocket поднимается только поверх HTTP/1.1; таблицы брендов
`Sec-CH-UA` и HTTP/2 SETTINGS переписаны с реальных браузеров и требуют сверки
при добавлении новой версии Chrome.

## Назначение

Инструмент сделан для тестирования: проверки мобильной вёрстки на реальном
наборе устройств, регрессионного тестирования собственных систем
антифрод/бот-детекта, исследований в области приватности и отпечатков браузера.
Используйте его на своих системах или там, где у вас есть разрешение.
