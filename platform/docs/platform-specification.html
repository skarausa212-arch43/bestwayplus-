Product specification · v1

The platform behind
Bestway Football

A public website, a client portal and an admin CRM — trilingual, GDPR-bound, and built around documents that must never leak. This document is the contract between the brief and the code: architecture, schema, permissions, flows, copy and the security model, followed by the foundation that now exists in the repository.

Section 01

Product definition and what changes

BESTWAY FOOTBALL becomes three products behind one brand: a public marketing site, an authenticated client portal, and an internal CRM. They share a design system, an identity provider and a database — nothing else. Treating them as one application is the single most common way projects like this fail, because a marketing page and a passport scan need opposite defaults.

Surface 01

Public website

Indexed, localised at /en, /pl, /ru, no authentication, no personal data beyond a contact form. Cached at the edge. Its job is credibility and conversion into Join the network.

Surface 02

Client portal

Authenticated, role-scoped, noindex. Profiles, documents, opportunities, messages. Every response is personal data, so nothing is cached and every query is scoped to the caller.

Surface 03

Admin CRM

Staff only, on /admin, ideally on its own hostname behind IP allow-listing. Holds the internal assessment fields that must never reach a client response.

Non-negotiable constraints

  • Authorisation is a backend concern. Hiding a button is a UX decision, not a security control. Every read and write passes a server-side policy check keyed on the session, never on a client claim.
  • Documents never become URLs. No file is served from the application origin and no storage key is guessable. Access is a short-lived signed URL issued after an authorisation check, and every issuance is logged.
  • Internal fields are a separate table. Internal rating, potential, marketability and comments live in player_internal_assessments, not as columns on the player profile. A leak then requires a deliberate join, not a forgotten select.
  • Verified means verified by staff. A user typing a FIFA licence number sets PENDING. Only an administrator moves it to VERIFIED, and the public badge reads from that column alone.
  • Consent is versioned and separable. Processing consent, profile-sharing consent and marketing consent are three rows, never one checkbox.
  • No invented content. No sample players, clubs, transfers, licences or partners ship in any environment that is not explicitly a seeded development database.
Regulatory position, carried into the product

The platform is a networking, coordination and administration tool. Where an action requires a FIFA Football Agent licence, the product must not imply Bestway performs it. This is enforced in three places: the public copy, the Representation block of the player profile (which records the player's own licensed agent), and the opportunity workflow, where the stage names describe coordination rather than negotiation on a player's behalf.

Section 02

Repository layout

A single repository, modular by domain rather than by file type. src/modules/<domain>/ holds the schema, service, policy and UI for that domain, so document logic is never scattered across four folders. Shared primitives live in src/lib, and src/messages/<locale>/ holds the catalogs.

Locale handling

  • English is the default and is still prefixed. /en/players rather than /players. A bare path redirects once, permanently, to the negotiated locale — no duplicate content, no ambiguity about the canonical form.
  • Detection order: explicit URL segment → locale on the signed-in user → NEXT_LOCALE cookie → Accept-Language → en.
  • Switching persists. The switcher writes the cookie for everyone and, for a signed-in user, also writes users.locale, which is what email templates read.
  • SEO: per-locale hreflang including x-default pointing at /en, one sitemap per locale, canonical self-referencing.
  • Never machine-translate at runtime. Catalogs are static JSON reviewed by a human; a missing key falls back to English and is reported, it does not silently render a key name.
Section 04

User flows

Flow A — Join the network (player)

1Role selectionPublic /join presents five cards. The choice is a route parameter, not stored state, so the form is linkable and the back button behaves.
2Account stepEmail, password, phone, preferred language. Password strength is checked server-side against a breach list; the email is checked for uniqueness without revealing whether it exists on the public error path.
3Consent stepTerms and privacy are required and recorded separately. Profile-sharing and marketing are optional, unticked, and each writes its own consents row with the policy version and the exact text hash shown.
4Account createdStatus PENDING_EMAIL. A verification email goes out in the user's chosen language. The user may enter the portal but cannot upload documents or be added to an opportunity until verified.
5Profile wizardPersonal → football → career → representation. Every step saves on blur, so a phone user who loses signal loses nothing. Completion percentage recalculates on each save.
6Document promptsThe checklist drives the user toward 100%. Nothing is mandatory beyond the account itself; the profile is usable at 40% and persuasive at 100%.

Flow B — Document request and fulfilment

1Staff raises a requestFrom the user's admin profile: type, message, optional due date. Writes document_requests and an activity row.
2User is notifiedIn-app notification plus a localised email. Both link to /portal/requests, never to a file.
3Upload intentThe client asks the API for an upload URL. The server authorises, validates declared MIME type and size, creates the document row as UPLOADED/scan:PENDING, and returns a presigned PUT valid for five minutes and bound to that content type and length.
4Direct uploadThe browser or phone camera uploads straight to storage. The application server never holds the bytes.
5Confirm and scanThe client confirms; the server verifies the object exists and matches the declared size, then queues a scan. An infected object is deleted, the row is marked, and staff are alerted.
6ReviewStaff move the document to APPROVED, ACTION_REQUIRED or REJECTED with a comment. The request closes automatically when a document of the requested type is approved.

Flow C — Opportunity lifecycle

1Created by staffClub, country, league, position, age band, salary band, transfer type, deadline. Visibility starts PRIVATE.
2Participants selectedStaff add specific players. Each addition creates an opportunity_participants row at stage NEW.
3Player sees itOnly the client-safe fields. internal_notes on both the opportunity and the participant row are excluded at the query level, not filtered in the component.
4Player respondsExpress interest, decline, or answer an information request. Stage moves NEW → PROFILE_UNDER_REVIEW → SUBMITTED.
5Staff drive it CLUB_REVIEWING, INFO_REQUESTED, NEGOTIATION, then SUCCESSFUL or CLOSED. Every transition is an activity row with actor and timestamp.

Flow D — Secure profile share

1Staff compose a linkPick the sections and the exact documents the recipient may see. Nothing is included by default.
2ConstraintsMandatory expiry, optional password, optional recipient label for the audit trail. The token is random, single-purpose and stored hashed.
3Recipient opens it/share/[token] renders only the allowed sections. Documents are still served by short-lived signed URL, scoped to the allow-list on the link.
4Tracking and revocationEach view writes a row with time, IP and user agent. Staff can revoke instantly; the player can see that a share exists.
Consent gate

A share link cannot be created for a player who has not granted the profile-sharing consent. The API rejects it; the button is disabled with an explanation. Consent withdrawal automatically revokes every active link for that player.

Schema decisions worth defending

  • Internal assessment is its own table. Not columns on player_profiles. A careless select * on the profile then cannot leak a rating, and the table can carry a stricter row-level policy.
  • Documents are soft-deleted and versioned. replaces_document_id keeps the chain, delete_locked is set the moment a document is attached to an active opportunity or an approved review, and hard deletion happens only through the erasure job.
  • Consents are immutable rows. Withdrawal writes revoked_at; it never updates granted. The full history is the evidence, and text_hash proves which wording was shown.
  • Activity logs are append-only. No update or delete grant for the application role; retention is handled by a partition drop, not a DELETE.
  • Row-level security as a backstop. The service layer is the primary control, but RLS policies keyed on current_setting('app.user_id') mean a bug in one query cannot return another user's rows.
  • Two indexes that matter early: documents(owner_user_id, status) for the review queue, and a trigram index over player name, club and nationality for admin search.

Conditions behind ◑

  • MANAGER sees and edits only the clients where users.responsible_manager_id is their own id. Escalation to another manager's client requires an ADMIN.
  • Own document deletion is allowed while delete_locked = false and the status is not APPROVED. Once a file is attached to an active opportunity or approved in a process, the user may request removal, which becomes a task rather than an immediate delete.
  • Stage advance by a client covers only the transitions offered to them — expressing interest or declining. Everything from CLUB_REVIEWING onward is staff-driven.
  • ADMIN erasure executes GDPR deletion but cannot delete audit rows; those are pseudonymised, keeping the action history while removing the identity.
How this is enforced

Every service method starts with authorize(session, action, resource), which throws before any query runs. UI permission helpers import the same module, so a hidden button and a rejected request are guaranteed to agree. Route handlers additionally re-check on the server even when called from a server component, because a server component is not an authorisation boundary.

The platform stores passports, contracts, medical records and bank details for EU data subjects. That places it firmly in the highest-care category, and the design has to show it rather than claim it.

MarketingConsentSeparate, optional, unticked. Withdrawable in one click from every marketing email and from Settings → Privacy.

Never bundle these

Processing consent and marketing consent are separate rows, separate checkboxes and separate withdrawal paths. Bundling them is the single most common GDPR failure on platforms of this shape, and it invalidates both.

Data subject rights, implemented

  • Access and export. Settings → Privacy → Export my data queues a job that produces a ZIP: profile as JSON, documents as originals, consent history, activity history. Delivered as a signed, expiring link, never as an email attachment.
  • Rectification. The profile is directly editable; corrections to staff-controlled fields go through a request that appears as a task.
  • Erasure. A deletion request sets DELETION_REQUESTED and starts a 30-day window, during which the account is inaccessible but recoverable. On execution, profile and documents are destroyed; audit rows are pseudonymised, not deleted, since retaining a record of processing is itself a legal obligation.
  • Restriction and objection. Withdrawing profile-sharing consent revokes every active share link immediately and blocks new opportunity assignments.
  • Portability. The export is machine-readable JSON, not a PDF.
  • Breach readiness. Document access logs make “which records were exposed” answerable within the 72-hour notification window.

Retention

Active account          for the life of the account
Deleted account         profile and documents purged; audit pseudonymised
Documents               purged with the account, or on expiry + 12 months
Consent history         6 years — it is the evidence that consent existed
Activity / access logs  24 months, then partition drop
Backups                 35 days, encrypted, EU region, erasure replayed on restore

Conventions

  • Every handler opens the same way: resolve session → authorize() → parse with zod → call the service. A handler that queries before authorising is a review failure, not a style preference.
  • Errors are shaped and localised. { error: { code, messageKey, fields } }. The client renders the key in the user's locale; the server never sends an English sentence to be shown.
  • Rate limits on login, registration, password reset, upload intent and download URL issuance — the last two because they are the expensive and the sensitive ones.
  • Idempotency keys on upload confirm and on anything that sends email.
  • No PII in URLs. Identifiers are UUIDs; filters go in the body for admin search.

Controls

Storage

Private by construction

Block Public Access enabled at the account level. No bucket policy grants *. Server-side encryption with a customer-managed KMS key. Versioning on, so a malicious overwrite is recoverable. Lifecycle rules move expired documents to a quarantine prefix before deletion.

Keys

Unguessable and meaningless

Keys are {uuid}/{uuid} with no filename, user id, name or document type. Enumeration reveals nothing, and a leaked key is useless without a signature.

Transport

Short-lived signatures

Upload URLs live five minutes and are bound to the declared content type and length, so a signed URL cannot be reused to upload something else. Download URLs live sixty seconds and force an attachment disposition, which stops a malicious SVG or HTML from executing on our origin.

Validation

Do not trust the extension

Allow-list of PDF, JPEG, PNG, HEIC and DOCX. Magic-byte sniffing on the worker, not the declared MIME type. Size ceiling enforced twice — in the signature and again on confirm.

Access

Every read is a record

document_access_logs records actor, document, action, IP and user agent for every issued URL — including staff and including share-link recipients. Downloading a passport or a bank document additionally requires a typed reason.

Deletion

Soft, then final

User deletion is a soft delete. delete_locked blocks removal while a document backs an active process; the request becomes a task instead. Hard deletion happens only in the erasure job, which also removes storage objects and all versions.

Things deliberately not done

No document is ever served from the application origin, so there is no /uploads/ path to guess and no proxy endpoint to confuse. No file name supplied by a user is used as a storage key. No document is attached to an outbound email — emails link into the portal, which re-authorises. And no thumbnail or preview is generated for identity documents, because a preview is a second, less-guarded copy.

Account and session security

  • Argon2id password hashing; minimum twelve characters checked against a breach corpus rather than composition rules.
  • Database-backed sessions in HttpOnly · Secure · SameSite=Lax cookies, so staff can revoke a session and a user can see and end their own.
  • TOTP two-factor, optional for clients and mandatory for every staff role.
  • Re-authentication before changing email, password or two-factor, and before any staff export.
  • Strict CSP, HSTS, no inline scripts, and no third-party script on any authenticated route.

Section 16

Everything that touches personal data stays in the EU, in one region, with a documented processor list. That is a legal requirement here, not an infrastructure preference.

Environments and release

  • Three environments. Local with docker-compose, staging with synthetic data only, and production. Production data is never copied downward — staging is seeded, never restored from a live dump.
  • Migrations run as a gated step before the new revision receives traffic; every migration is reversible or ships with a written rollback.
  • CI runs typecheck, lint, unit tests, a policy test suite that asserts the permission matrix, and a build. The policy suite is the one that must never be skipped.
  • Backups daily with a 35-day window, plus a quarterly restore drill that is actually performed and recorded.
  • DNS. bestwayfootball.pl for the public site and portal; admin.bestwayfootball.pl for the CRM, so it can carry IP allow-listing and its own WAF rules without affecting clients.
