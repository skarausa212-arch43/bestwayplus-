# LUMI — native app (Android, iOS later)

A thin **Capacitor** shell that opens **https://lumi24.pl** directly. Nothing of
the interface is bundled: the design, the logic and even the push handling are
served from the site, so **a change you deploy is live in the app the moment it
reaches the server — no new APK, no store review, no waiting for users to
update.** That is the whole point of this shape.

What the shell adds on top of a browser tab, and why the app exists at all:

* **native push** — a provider hears about a new job with the app closed;
* **App Links** — a `lumi24.pl` link from an email opens in the app;
* **hardware access** — GPS for the booking pin and nearest-first dispatch, the
  camera for before/after photos;
* **home-screen presence** and a launch screen instead of a browser chrome.

```
public/                  ← the web app. It also carries the native bootstrap
                           (push registration, deep links, Android back button),
                           guarded by Capacitor.isNativePlatform() — so it is a
                           no-op in a browser and updatable from the server.
mobile/
  capacitor.config.json  ← server.url = https://lumi24.pl  (the remote-load switch)
  www/                   ← generated: only an offline page for the very first
                           launch without network (server.errorPath)
  assets/                ← icon.png · icon-foreground.png · icon-background.png
                           splash.png · splash-dark.png   (the sources you edit)
  android/               ← generated by `npm run android` (not in git: it is
                           fully described by the config + scripts above)
  scripts/               ← sync-web · place-firebase · patch-gradle ·
                           patch-manifest · patch-strings · gen-assets
```

## What updates without touching the app

| Change | Needs a new APK? |
| --- | --- |
| Screens, texts, prices, new service category | **No** — deploy the site |
| New language, design, whole new section | **No** |
| Push message content and routing | **No** — the handler ships from the site |
| New Capacitor plugin (e.g. biometrics) | Yes |
| Permissions, app icon, package name | Yes |
| Android SDK / target API bump | Yes |

In practice: once or twice a year, not on every release.

## Build it

You need **Android Studio** (SDK + build tools) and a **Google Play** developer
account ($25 once). Node and the Capacitor project are already set up here.

Every command below runs **inside a clone of this repository** — `cd mobile`
only works from `…/bestwayplus-/cleango`. On a fresh machine:

```bash
git clone -b claude/cleango-app-yd4rzj https://github.com/skarausa212-arch43/bestwayplus-.git
cd bestwayplus-/cleango/mobile
```

Then:

```bash
npm install
npm run android          # creates/refreshes the project + applies every patch
npx cap open android     # opens Android Studio
```

`npm run android` is idempotent — run it after any change to
`capacitor.config.json`, and after pulling new code.

In Android Studio: *Build → Generate Signed Bundle / APK → Android App Bundle*.
Create the keystore when it asks and **keep it safe** — Play ties the app to that
key forever, and losing it means publishing under a new listing.

Debug build to try it on a phone right away: *Run ▶* with the device connected.

## Icon, splash and app name

These are the three things that genuinely live in the binary, so changing them
does mean a new build — unlike everything on the site.

**Name under the launcher icon** — `capacitor.config.json` → `appName`. Then
`npm run android`: `patch-strings.js` writes it into
`android/app/src/main/res/values/strings.xml`. (Capacitor itself only writes
that file when it first generates the project, which is why the patch exists —
without it, editing `appName` later changes nothing.) The name in the Play
listing is separate and set in the Play Console; they don't have to match, but
users notice when they don't.

**Icon and splash** — the mark is a dark house with one window lit, because
*lumi* is light, and because a home screen has enough green houses on it
already. It is drawn as vector source in `scripts/make-brand-assets.js`, not
kept as five exported PNGs nobody can edit: change a colour or the geometry
there, then

```bash
npm run brand      # redraws the five sources in assets/
npm run assets     # rasterises every Android density from them
```

The five sources, and what each is for:

| File | What it is | Size |
| --- | --- | --- |
| `icon.png` | legacy square icon, full bleed | 1024×1024 |
| `icon-foreground.png` | adaptive icon: the mark + its glow, transparent | 1024×1024 |
| `icon-background.png` | adaptive icon: the ground the mark sits on | 1024×1024 |
| `splash.png` | launch screen, light | 2732×2732 |
| `splash-dark.png` | launch screen, dark | 2732×2732 |

Three constraints Android imposes, all handled in the script:

* the adaptive icon is cropped to a circle, squircle or rounded square depending
  on the launcher, and only the central **~61%** is guaranteed to survive. The
  script asserts the mark's furthest corner against that radius and **fails the
  build** rather than shipping a roof that gets clipped on phones we don't own;
* the two adaptive layers move independently (parallax), so the glow lives in
  the *foreground* with the window it comes from — split across layers it would
  visibly drift away from its own light source;
* the splash is centre-cropped at every aspect ratio, so the mark sits in the
  middle third and the flat ground carries the edges (`#F4F8F5` light /
  `#0C100E` dark, set in `scripts/gen-assets.js`).

Replacing the artwork wholesale is still fine — drop your own PNGs into
`assets/` at the sizes above and run `npm run assets` alone, skipping `brand`.

**Package name** (`appId`, `pl.lumi24.app`) is not a branding field — it is the
app's identity in Play forever. It cannot be renamed in place; a different one
is a different app with a different listing and no existing installs.

### Firebase (push)

Push works only with the Firebase project the server already uses. Download
`google-services.json` (Firebase → Project settings → *Your apps* → Android, with
package `pl.lumi24.app`), drop it into `mobile/`, then:

```bash
npm run place-firebase && npx cap sync android
```

Without it the app builds and runs; only push stays silent.

### App Links (lumi24.pl opens in the app)

Android verifies the claim against the site. After the first signed build:

```bash
keytool -list -v -keystore <your.keystore> -alias <alias> | grep SHA256
```

Put that fingerprint on the server in `deploy/instance.local.env`:

```
LUMI_ANDROID_CERT_SHA256=AB:CD:…:EF
```

The server then serves it at `/.well-known/assetlinks.json` and Android starts
routing links into the app. Until then links open in the browser — a safe
default, nothing breaks.

> Play App Signing re-signs your upload with Google's key. Take the fingerprint
> from *Play Console → Setup → App integrity → App signing key certificate*, not
> from your upload keystore, or verification silently fails.

## Play Console listing

* **Package**: `pl.lumi24.app` · **App name**: LUMI
* **Privacy policy URL**: `https://lumi24.pl/privacy.html` (required — the app
  collects location and, through the site, identity documents)
* **Data safety**: declare location (approximate + precise, for matching a
  provider), photos (before/after reports), name/e-mail/phone, and payment info
  handled by Stripe. All of it is collected, transmitted encrypted, and deletable
  — the account deletion flow is in the app.
* **Category**: House & Home · **Target audience**: 18+
* **Permissions**: location and notifications are both prompted in context and
  explained on screen before the system dialog.

> **One policy risk, stated plainly.** Google rejects apps that are only a
> website in a frame ("minimum functionality"). This one adds push, App Links,
> GPS and camera, which normally clears that bar — but write the listing around
> what the app *does* (ordering and tracking a cleaner, receiving alerts), not
> around "our website in an app". If a reviewer pushes back, the answer is the
> native functionality, and it is real.

## Toolchain and the API level Play demands

Capacitor 8 · `targetSdk`/`compileSdk` **36** (Android 16) · `minSdk` **24**
(Android 7.0) · AGP 8.13 · Gradle 8.14.3 · JDK 21 (the one Android Studio
bundles).

The target API level is not a preference — Play enforces it at upload. New apps
must target **API 36 from 31 Aug 2026**, and API 35 before that; an app built
against 34 is rejected at the door, before any review. Capacitor 8 ships the
whole tested set (AGP, Gradle, AndroidX, target 36) together, which is why the
project is on it rather than on a hand-bumped older version.

`minSdk 24` is Capacitor 8's floor. It drops Android 5.x–6.0, which is a
fraction of a percent of Polish devices and below Play's own support horizon.

## Versioning

`android/app/build.gradle` → `versionCode` (integer, +1 every upload) and
`versionName` (what users see). Because the content is remote, these change
rarely — bump them only when you actually ship a new binary.

## Offline

First launch with no network shows `www/offline.html` and a retry button. After
one successful load the site's own service worker has the shell cached, so later
launches open offline and show live data as soon as the network returns.
